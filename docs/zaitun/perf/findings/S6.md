# S6: delivery

Search track. No product code changed. Scripts: `scripts/perf/S6/` (`delivery.mjs`, `variants.mjs`, tests). Raw results: `scripts/perf/results/2026-11-22T14-20-33-S6-variants/variants.json` and `…14-00-48-S6-headers/headers.json` (the second run of the header audit, with raw wire sizes, is the one quoted here).

Build measured: the production build of `main` at 692ea51 (after F2A, S3's findings not applied), local mode, rig lock held, on AC power. Phone profile = QA's (Fast 4G, 4× CPU, low tier); desktop = unthrottled localhost, so desktop times say nothing about delivery and only its byte counts are used. Phone numbers are the median of three fresh browsers, shaders cached on this Mac (S1: a first-ever visit adds seconds that no delivery change touches).

**The host is not known** (STATUS owner input "Where the site is hosted" is still missing). Everything below is what the app sends to a plain `next start`. Rows marked *host* may already be done, or impossible, depending on the answer.

## Summary

- **Nothing in `public/` is cached beyond a revalidation.** Every model, texture page, the decoder and the manifests answer `Cache-Control: public, max-age=0`. A repeat visit on the phone profile makes 24 conditional round trips (9.6 KB) before the scene can start. With long cache lifetimes: 2 trips, 4.3 KB, **live scene 1.77 → 1.49 s (−0.28 s, −16%)**. It is only safe once the file names change with the content (F2B), because today's names do not.
- **The model request starts 2.6 s into the load on the phone profile** and finishes at 5.07 s. A preload hint in the document's first response starts it at about 0.2 s. Measured on its own: **live scene 5.43 → 5.18 s (−0.25 s)**. The tier is chosen in the browser, so the hint cannot come from the server alone (S6-1).
- **Brotli** saves 0.21 MB before the live scene on the phone tier (3.60 → 3.39 MB, −6%) and 0.69 MB on desktop. Only useful if the host does not already do it (S6-3, *host*).
- All three together: phone live scene **5.43 → 4.88 s (−0.55 s, −10%)**, first-visit bytes 3.60 → 3.39 MB, repeat visit 9.6 → 4.3 KB. Not enough alone for the 5 s target on a first-ever visit (S1's shader link time is separate), but it takes the shaders-cached case under it.
- `proxy.ts` runs on every `.glb`, `.ktx2`, `.wasm`, `.mp3`, `.js` and `.json` file in `public/` (30 files, about 40 MB; 11 of the first-visit requests on Home). In local mode that costs 0.32 ms each, so no time gain; in Supabase mode it is a session check per asset (S6-5).

## What I could not measure

- **The host.** No numbers for edge brotli, HTTP/2 or 3 (the rig serves HTTP/1.1, six connections per host), early hints, or cache behaviour in front of Next. S6-3 and the `Link` header part of S6-1 depend on it.
- **Supabase mode** (`proxy.ts` cost with a real session check); the rig runs in local mode.
- **A real phone**, or a first-ever visit: the shader link time (S1) dominates there and delivery changes do not touch it.
- **Desktop time:** unthrottled localhost, so only bytes are used. The desktop live-scene time alternates between 1.0 s and 1.3 s from run to run whatever the variant is.

## Method notes

- `variants.mjs` puts a small front server between Chrome and the rig's build. Only delivery changes (encoding, `Cache-Control`, a `Link`/preload hint); file contents are the shipped bytes. Brotli is level 11, compressed before timing so it never lands in a timed load. The front server answers conditional requests with 304 like the real one.
- A load is classified from the DevTools network events: served from cache, a conditional round trip (answer under 600 bytes) or a download. Chrome reports a 304 revalidation as status 200, so the status code cannot be used.
- Repeat visit = second load in the same browser context, HTTP cache kept, same throttling.
- The Mac is on AC; the first attempt ran on battery and its numbers were discarded.
