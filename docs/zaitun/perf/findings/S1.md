# S1 findings: page load and 3D start-up on the main thread

Search track S1 of the [optimization plan](../../OPTIMIZATION_PLAN.md), 2026-11-21 and 22. Scope: what blocks the main thread while Home loads and the 3D starts, what could move, be spread or wait, which client files must be client code, and fonts, CSS and layout shift on the critical path. No product code changed. Scripts are in `scripts/perf/S1/` on branch `zaitun/S1` (worktree `.claude/worktrees/zaitun-S1`, not committed); raw results are in that worktree's `scripts/perf/results/*-S1-startup/` (git-ignored). The baseline is [BASELINE.md](../BASELINE.md).

## The short version

- **The 2–3 s stall is the first-ever compile of the scene's shaders, forced onto the main thread.** The first time three.js uses each shader program it asks the GPU for the link log, and that call waits until the program has finished compiling and linking. Nothing is compiled before the first frame, so all the waits land in it, one program after another.
- **How long it lasts depends on whether the GPU's shader cache has seen the shaders.** On this Mac the first-frame task is 0.3 s when they are cached and **4.1–4.2 s on the phone profile (6.7–6.9 s on desktop) when they are not**, which is the case for every first-time visitor. The rig's baseline (0.68 s of blocking) is the cached case.
- **Compiling ahead, without blocking, removes most of it.** Tried from outside the app: the first-ever visit's longest task falls from 4.19 s to 0.76 s on the phone profile and the scene appears 2.2 s sooner (S1-1).
- **Three more long tasks are our own code**, not three.js: the ground mesh built in code when the canvas mounts (154 ms), the sky reflection map (57 ms), and the position of every tree worked out on every visit (146 ms). All three give the same result each time and can be made ahead (S1-3 to S1-5).
- **With S1-1, S1-3, S1-4 and S1-5 the cached case meets the stall target** (about 0.3 s of blocking, no task over 200 ms). The first-ever visit does not yet: about 1 s remains (S1-1, S1-2).
- **The LCP image (the poster) is fetched at low priority**, and Arabic fonts weigh on both languages (S1-8, S1-9).

## How it was measured

Everything ran through the P0 rig (it holds the measurement lock), on the production build of `main` at 09684f0, on the baseline's machine and profiles: the **phone profile** (412 × 915, 4× CPU, Fast 4G, low tier) and the **desktop profile** (1440 × 900, no throttling, high tier). Each load is a fresh Chrome. `scripts/perf/S1/startup.mjs` records a load in these modes:

| Mode | What it records |
|---|---|
| `trace` | A Chrome trace with the CPU profile. `analyze.mjs` lists every main-thread task over 50 ms and what ran in it: timeline events, script files, WebGL calls, the functions on top. The build has no source maps, so `where.mjs` prints the built code at a profile position to name the function |
| `gl` | Every WebGL call timed inside the page (`glprobe.js`): shader work, uploads and draws, and which shader programs are linked when |
| `salt` | As `gl`, with one unused, uniquely named uniform added to every shader, so no cache anywhere has seen it. This is what a first-ever visit compiles. Start-up numbers only: never frame rates or reference frames |
| `precompile` | What-if: holds the first frame back while every program it needs is compiled with three.js's `compileAsync` (the browser compiles in the background, the main thread only polls), then lets frames through |
| `nocheck` | What-if: turns three.js's shader error check off |

Limits to keep in mind:

- **The trace and the call timer slow the page a little** (the first-frame task reads 305–352 ms traced against 273 ms in the baseline). Read these numbers for shares and for before-and-after within one mode; the plain rig numbers stay the reference.
- **"Blocking" here** is the part of each task beyond 50 ms from first content until 1.5 s after the scene's first frame (the baseline uses 1 s).
- **The GPU is this Mac's.** The phone profile slows the CPU four times but not the GPU process, so shader compile times are a Mac's. A real phone compiles more slowly and has its own cache; the real-phone session should time a first visit and a second one.
- **Medians of three loads** unless a row says otherwise.

## The stall, named (K1, P7)

### Where the time goes

three.js builds a shader program the first time a material is drawn. With `renderer.debug.checkShaderErrors` on (the default), the program's first use calls `gl.getProgramInfoLog`, which cannot return until the GPU process has compiled and linked it. The experience holds its frame loop until the model is in (`frameloop="never"` in `ExperienceCanvas.tsx`), then draws the first frame through the effect composer (`RenderPass` in `ExperienceRoot.tsx`); nothing asks for the programs earlier. So the first frame links every program of the scene and of the effect chain in one task.

| | Phone profile (low tier) | Desktop profile (high tier) |
|---|---|---|
| Programs linked before the first picture / in all | 30 / 34 | 51 / 60 |
| Shaders cached: link waits | 29 × about 5 ms = **141 ms** | 48 × about 4 ms = **207 ms** |
| Shaders cached: first-frame task | 305–352 ms (six traced loads) | 295–298 ms |
| First-ever visit: link waits | 29 × about 146 ms = **4.25 s** (worst 212 ms) | 48 × about 142 ms = **6.83 s** (worst 228 ms) |
| First-ever visit: first-frame task | **4.11–4.22 s** (four loads) | **6.68–6.92 s** (four loads) |
| First-ever visit: live scene | 11.2–11.3 s (cached: 7.1–7.3 s) | 8.0–8.2 s (cached: 1.2–1.4 s) |
| First-ever visit: blocking | 4.99 s (cached: 0.83 s) | 7.22 s (cached: 0.31 s) |

The cached first-frame task on the phone profile, from the traces (median of three, 312 ms): link waits 125 ms, building the shader text 68 ms (`acquireProgram`: includes, loop unrolling and defines for 30 programs, CPU work at 4×), texture and buffer uploads 7 ms, the rest three.js and the effect chain.

### Why it came and went

The cache that matters is not the browser's. On macOS the system keeps compiled Metal shaders per application (`…/C/com.google.Chrome.helper/com.apple.metal`, about 150 MB here, rewritten during rig runs), and it survives a new browser, a new profile and a new build. That explains every earlier sighting:

- **QA's 2–3 s and P0's single 3.0 s (phone) and 4.3 s (desktop) task:** loads where that cache did not have the scene's shaders yet.
- **P0's twelve fresh-browser loads that never showed it:** a fresh browser still reads the system cache, so they were all cached loads. The "cold" column of the baseline's load trace is not a first visit.
- **In between:** the first traced load of this track on each profile waited 661 ms (phone) and 911 ms (desktop) on links, and the next ones 136 and 213 ms: a partly filled cache.

A first-time visitor has nothing cached, on any system. The salted runs are the repeatable version of that visit, and they land where P0's and QA's sightings did.

### The second hitch: the first quality step

Each tier starts one quality level below its best (`quality.ts`) and steps up about 2.5 s after the first frame. The new effects' programs are then built the same blocking way, as the poster hold ends and the camera starts to move.

| | Phone profile (level 0 to 1) | Desktop profile (level 2 to 3) |
|---|---|---|
| Programs built at the step | 4: edge smoothing (2), light shafts, the effect pass | 9: seven unnamed shader materials (ambient occlusion comes on at level 3), the effect pass, a copy pass |
| Shaders cached | 12 ms | 28 ms |
| First-ever visit | 290 ms, one task of 311–313 ms | 850 ms, one task of 862 ms |

## Long tasks on the phone profile, shaders cached

Three traced loads (2026-11-21, 20:46 UTC); times are since navigation, medians.

| Task | Starts | Lasts | What runs in it |
|---|---|---|---|
| 3D code evaluated | 2.07 s | **146 ms** (143–150) | The two lazy chunks (1.2 MB and 0.53 MB raw) are instantiated: 142 ms in the bundler's module set-up, mostly compiling the module functions |
| Canvas mounts | 2.30 s | **357 ms** (353–367) | Ground mesh built in code 154 ms (land-use lookups 60, vertex normals 24); sky reflection map (PMREM) 57 ms, with its own four programs linked on the spot; renderer and React Three Fiber root 40 ms; the rest is React mounting the scene |
| Plants arrive | 4.25 s | **190 ms** (187–195) | Vegetation field built when its library lands: 165 ms, of which working out where every plant goes (`planLandscape`) 146 ms, with 75 ms of land-use lookups inside it |
| First frame | 6.94 s | **312 ms** (305–314) | See above: link waits 125 ms, shader text 68 ms |
| Smaller tasks | 0.7 s | 55–77 ms | The first-render scripts registering (twice in some loads) |

Blocking adds up to 0.83 s with the trace running. On the desktop profile the same tasks are 152 ms (mount), 52 ms (plants) and 297 ms (first frame, 241 ms of it link waits).

Before the 3D code arrives the main thread is not the problem: from navigation to 2.04 s it does 0.51 s of work at 4× (0.26 s the browser's own parsing, style, layout and paint; 0.24 s script), with no task over 77 ms.

## What-ifs, measured

Both switches change the shipped page from outside (`glprobe.js`), so a fix has a number before anyone writes it.

### Compile ahead (`precompile`)

| | Phone, cached | Phone, first-ever visit | Desktop, cached | Desktop, first-ever visit |
|---|---|---|---|---|
| Longest task, as shipped | 325 ms | 4.19 s | 275 ms | 6.72 s |
| Longest task, compiled ahead | 297 ms (the mount; the first frame is 103 ms) | **0.76 s** | **130 ms** | **1.55 s** |
| Blocking, as shipped → compiled ahead | 834 → 638 ms | 4.99 → 1.69 s | 311 → 109 ms | 7.22 → 2.74 s |
| Live scene, as shipped → compiled ahead | 7.24 → 7.14 s | 11.32 → **9.10 s** | 1.42 → 1.32 s | 8.06 → **4.24 s** |
| Background compile took | 111 ms | 1.03 s | 77 ms | 1.20 s |

Two things follow. The wait leaves the main thread, and the compile itself gets faster, because the driver compiles programs side by side instead of one at a time (4.25 s of waits become 1.03 s of background compile on the phone profile).

What is left on a first-ever visit after compiling ahead (phone profile):

| Task | Lasts | Why |
|---|---|---|
| Canvas mounts | 592 ms (cached: 297) | The reflection map's four programs still link on the spot, at 62–87 ms each |
| First drawn frame | 759 ms | Each program still costs about 23 ms on its first use although the driver reported it complete (about 30 ms each on desktop, a 1.51 s task). On this Mac the Metal backend seems to finish part of the work at first use |
| First quality step | 313 ms | The step's programs were not compiled ahead |

### Shader error check off (`nocheck`)

No gain. The wait moves to the next call that needs the linked program (`getProgramParameter(ACTIVE_UNIFORMS)`: 58 calls, 127 ms, against 141 ms in `getProgramInfoLog`). Longest task 288 ms against 325 ms on the phone profile and 279 against 275 ms on desktop, inside run-to-run spread.

## Client files

There are 38 files marked `"use client"`. Every one uses state, effects, event handlers or browser APIs, so none can become a server component as it stands. The question that matters is where each one is loaded.

| Group | Files | Needed by | Loaded on public pages today |
|---|---|---|---|
| Admin panel (`components/admin/**`, `app/admin/(panel)/error.tsx`) | 9 | Admin only | no |
| Inline editor (`components/editable/**`) | 11 | Edit mode only | **yes**: 165 KB gzip on every public page (P3, S1-10). `EditPageLauncher` is the only one a visitor's page needs, and it is small |
| Experience shell (`ZaitunExperience`, `ExperienceHud`, `Joystick`, `UnitPanel`) | 4 | Home | yes, on every page; the last three are only shown once the scene runs |
| Experience 3D (`ExperienceCanvas`, `StoryScroll`) | 2 | Home, capable devices | no: already lazy |
| Finder (`components/sawad/finder/**`, `SceneViewport`, `SceneCanvas`) and `ContactForm` | 7 | Residences, Contact | yes, on every page (one shared chunk) |
| Site chrome and monitoring (`NavDisclosure`, `HtmlLang`, `ErrorBoundary`, `useReportError`, `global-error.tsx`) | 5 | Everywhere | yes, and small |

Server-rendering more of the experience shell would gain little: the whole shared chunk costs 31 ms of script at 4× before the 3D code arrives, and hydration shows no long task. The hero, the beats and the captions already arrive as server-rendered children.

## Fonts, CSS and layout shift

- **Layout shift on Home is 0** (Lighthouse, both forms). Nothing to fix here.
- **Fonts.** The two Latin fonts (43 KB) are preloaded through the response's `Link` header and display with `swap`. The Arabic ones are S1-9.
- **CSS.** Three render-blocking files, 24 KB on the wire (76 KB, 14 KB and 11 KB raw); the largest carries 34 `@font-face` rules. Lighthouse estimates 300 ms on its slow connection. Small against the rest; left as it is.
- **The poster** is S1-8.

## Ruled out ("no gain")

| Candidate | Measured | Verdict |
|---|---|---|
| Turn off three.js's shader error check (`renderer.debug.checkShaderErrors = false`) | The link wait moves to the next call: 127 ms against 141 ms; longest task 288 against 325 ms (phone), 279 against 275 ms (desktop) | no gain |
| Move model parsing and geometry decoding to a worker | Geometry (meshopt) decoding is 25 ms on the main thread at 4× for the low model; no task over 50 ms between the plants arriving and the first frame | no gain |
| Texture and buffer uploads as the cause of the first-frame stall | 10–12 ms of texture uploads and 5–10 ms of buffer uploads on the phone profile | not the cause |
| Hydration as the cause (QA's first diagnosis) | No task over 77 ms before the 3D code arrives | not the cause |
| The browser's own shader cache as the explanation of the stall | A fresh browser and profile are still cached loads; only shaders the system has never seen are slow | not the cause |
| Server-render the experience shell instead of client code | The shared chunk costs 31 ms of script at 4× | no gain against the stall |
| The scroll driver (GSAP) | 37 ms of script at 4× when its chunk arrives; one 53 ms task in one load of five | no gain |

## For other tracks

- **S2:** the eager script list and what is in it (S1-10); the two lazy chunks cost 146 ms to evaluate (S1-6). The 230 KB chunk compresses poorly (0.53 MB raw), which suggests embedded data.
- **S4, S5:** the hitch 2.5 s after the first frame is the quality step's shader builds (S1-2). The baseline's "one frame of 217–267 ms when the scene appears" (P7) is the first-frame task of S1-1.
- **S6:** S1-7 splits P6's 1.3 s into 0.77 s waiting for the 3D chunks and 0.5 s of main-thread work.
- **F1, F3:** `node scripts/perf/S1/startup.mjs --modes gl+salt --profiles phone,desktop` is the first-ever-visit number to compare before and after; `--modes trace` gives the task table.
- **P0 (rig):** the rig stops with an error in a worktree that has no `node_modules` of its own (`machineInfo` reads the Next version from the checkout; worked around with `pnpm install` there). The measurement lock is not first come, first served: a session that runs several rig scripts back to back keeps the others waiting until its chain ends. The load trace's "cold" label is a cached load (see above).
