# S5 findings: work per frame and memory

Search track S5 of the [optimization plan](../../OPTIMIZATION_PLAN.md), 2026-11-21 and 22. Scope: the JavaScript each frame runs (culling, the plant sort, people, cars and birds, the tour driver, the scroll), objects made inside frame loops, React re-renders caused by frame state, hitches after the first frame, leaks on close and on route change, and what happens when the GPU context is lost. No product code changed. Scripts in [scripts/perf/S5/](../../../../scripts/perf/S5/README.md) (branch `zaitun/S5`); raw outputs in `scripts/perf/results/*-S5-*` in that worktree (git-ignored). The baseline is [BASELINE.md](../BASELINE.md).

## How it was measured

All on the P0 rig: production build of `main` at 09684f0, served locally, measurement lock held, on the charger (two follow-up runs for S5-13 on battery, see the note under the findings). High tier = desktop profile (1440 × 900 at 2×, no throttling); low tier = phone profile (412 × 915, **4× CPU slowdown**). Each camera is a fresh load, recorded from a fixed frame of a frame-exact plan.

- **Per frame**: an extra probe ([probe-s5.js](../../../../scripts/perf/S5/probe-s5.js)) times the requestAnimationFrame callback that draws, every other rAF callback of the same frame, and each React Three Fiber `useFrame` subscriber, named from its owner component's props ([labels.mjs](../../../../scripts/perf/S5/labels.mjs)); it tallies bytes uploaded to the GPU (`bufferSubData`, `texSubImage*`, …) and sees every React commit through a minimal DevTools hook. 8 cameras ([shots-s5.mjs](../../../../scripts/perf/S5/shots-s5.mjs)) × 2 tiers × 2 runs, adaptive quality; plus the high tier pinned at levels 2 and 3 on three cameras.
- **CPU profile**: V8's sampling profiler (100 µs) over the same windows, self time per function per frame.
- **Allocations**: V8's sampling heap profiler (1 KB interval) and a GC trace over the same windows.
- **Leaks**: heap snapshots diffed by constructor over six Home → Compounds → back cycles and six Explore → Back cycles; on Compounds, what the hidden Home still does (render calls and main-thread busy time per second, R3F's frame loop setting). Plus the sound and the walk's key handlers across a route change.
- **Context loss**: `WEBGL_lose_context` in the story and while exploring, then `restoreContext`.

Cameras: `stop-2` held still, `opening`, `scroll-sweep` (6 s from the top to the last beat), `fling` (jump to the last beat), `circuit` (the idle tour at the top), `orbit-drag` (2 s drag), `walk-long` (W held 5 s with a turn), `explore-idle`.

`performance.now()` is coarsened to 0.1 ms in this page, so per-subscriber numbers are means over 150–710 frames; the CPU profile gives the finer split.

| Camera | High: callback (p95) | High: top items (mean) | Low, 4× CPU: callback (p95) | Low: top items (mean) | GPU uploads / frame, high / low |

| opening | 2.1 ms (3.3) | draw 1.8, plants 0.17, camera 0.17 | 4.4 ms (7.0) | draw 3.6, camera 0.44, plants 0.26, life 0.20 | 0.56 MB / 0.21 MB |
| scroll-sweep | 3.1 ms (4.4) | draw 2.4, plants 0.36, camera 0.19 | 4.8 ms (6.9) | draw 3.2, plants 0.6, camera 0.6, life 0.27 | **2.19 MB / 0.73 MB** |
| fling | 2.7 ms (5.3) | draw 2.4 | 4.4 ms (8.5) | draw 3.4 | 1.65 MB / 0.61 MB |
| circuit | 2.1 ms (2.8) | draw 1.9 | 4.0 ms (5.6) | draw 3.5 | 0.29 MB / 0.09 MB |
| orbit-drag | 3.3 ms (4.6) | draw 2.3, **plants 0.80** | 4.9 ms (6.5) | draw 3.3, **plants 1.07** | **3.33 MB / 1.08 MB** |
| walk-long | 2.7 ms (3.9) | draw 2.5 | 2.9 ms (4.7) | draw 2.4 | 0.36 MB / 0.06 MB |
| explore-idle | 2.6 ms (3.8) | draw 2.4 | 3.7 ms (5.6) | draw 3.3 | 4 KB / 1 KB |

"draw" is the render pass (the effect composer and three's render, including its scene traversal); "plants" SceneVegetation; "camera" StoryRig; "life" SceneLife. Every other subscriber (InstanceCulling ≤ 0.13 ms, PostFX, Daylighting, sky, water, drei's PerformanceMonitor) is ≤ 0.13 ms at 4× CPU. Time outside the subscribers (React Three Fiber's own loop) and in other rAF callbacks (GSAP's ticker) rounds to 0 (p95 ≤ 0.8 ms in the sweep).

**What this says**: JavaScript per frame is not what limits the frame rate. Even at 4× CPU the worst p95 is 8.5 ms, and 75–90% of every frame is the draw itself, whose cost is set by what is drawn (S4, F2B). The per-frame work that does scale badly is the plant sort and its GPU uploads (S5-5) and the garbage the frame makes (S5-6, S5-7). The hitches after the first frame are level changes (S5-3, S5-4), not JavaScript, apart from one unexplained run (S5-12). The two findings a visitor sees are not per-frame work at all: the site without its buildings on every return to Home (S5-13), and the hidden Home still drawing on other pages (S5-1).

## For the ledger (T)

- P1: cause found (S5-1); the fix needs the imperative pause, a prop change cannot reach a hidden Canvas.
- P2: mechanism confirmed and worsened by S5-3's fix (S5-9); fix both together.
- P8: no leak in the JS heap (S5-11); the 46 MB of array buffers kept after the first return is S5-13.
- S5-13 is the most visible finding: every return to Home shows the site without its buildings while the whole scene reloads.
- New and outside S5's scope but found here: S5-3 (the monitor's fallback) belongs with S9's thresholds; S5-12 needs RS and the real phone.
- Ownership gap: `scene/landscape.ts` and `scene/lifeMotion.ts` (S5-6) are not in any fix track's list.
