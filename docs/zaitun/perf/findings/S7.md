# S7 findings: server and data

Search track S7 of the [optimization plan](../../OPTIMIZATION_PLAN.md), 2026-11-22. Scope: time to first byte on the catch-all route, database calls per page and what is cached, the media route, image sizing, and the cost of `proxy.ts` and `instrumentation.ts` on each request. No product code changed. Scripts in `scripts/perf/S7/` (branch `zaitun/S7`, worktree `.claude/worktrees/zaitun-S7`); raw output in `scripts/perf/results/S7-request-all.json` there (git-ignored). Baseline: [BASELINE.md](../BASELINE.md).

## Short answer

**The server is not a lever for any section 1 target.** Every published page is prerendered and served from cache in 1–3 ms (local, median of 20) with no database call at run time. Nothing here moves the Lighthouse score, the live-scene time or the transfer numbers. What S7 found is robustness: how the site behaves for addresses that are not pages, after a publish, and on more than one server. Those depend on the hosting answer, which is still missing.

## How it was measured

P0 rig: production build of this checkout (`main` at 692ea51, no product change), served locally, measurement lock held, on the charger. `node scripts/perf/S7/request.mjs all --runs 20` does two things.

- **Local mode** (the rig's own build, sample data from files): per page the first request, then 20 repeats, streamed, reading time to first byte, time to the first byte of `<main id="main"` (the page, as against the skeleton shell) and to the end; response headers; public files; the image optimizer.
- **Supabase mode**: a second build (a clone of the rig's snapshot, in its own folder) with `NEXT_PUBLIC_SUPABASE_URL` pointing at a mock PostgREST on port 54329. The mock serves the seed data, adds 40 ms per query and counts every query by table. It exists because the rig has no Supabase project and `NEXT_PUBLIC_*` values are fixed at build time. It shows how many calls the code makes, not how long a real Supabase takes.

Limits: loopback means no network time; the Mac's CPU, not a host's. Round-trip counts are the portable number.

## Ruled out (no gain)

- **Time to first byte on the catch-all route.** 1–3 ms for published pages in both modes; the HTML is complete in the first response (the content marker arrives within 0.3 ms of the first byte). The `PageSkeleton` fallback is never what a visitor waits on for a known page.
- **Database calls per page.** Zero at run time for known pages, on the first visit and on repeats; 26 queries at build. Caching (`"use cache"`, `cacheLife("max")`, tags) is doing its job.
- **`instrumentation.ts`.** `onRequestError` runs only when a request fails; no cost otherwise.
- **`proxy.ts` on pages and files for anonymous visitors.** No network call, no measurable time (see S7-5 for the matcher). With a login cookie it verifies the token on every request, which only editors have.
- **Image sizes in the markup.** `sizes` is set on every `Image`, widths come from Next's default list, and the output is 4–157 KB WebP, 5–25× smaller than the JPEG sources (S7-4 is about the first encode, not the size).
- **Media route cache headers.** Correct.

## Ledger notes

- **P4** (models served gzip at best) is confirmed from the server side, and so is the `public/` file cache lifetime: `.glb` and `.mp3` come back `public, max-age=0`, the poster JPG `s-maxage=60, stale-while-revalidate=3540` (no browser freshness), the favicon `max-age=0, must-revalidate`. That is S6's finding to carry (F5).
- **P3** (admin packages on every public page) and the cold-start numbers are S2 and S1's; S7 saw nothing server-side that adds to them.
- Nothing from S7 should be ranked above S1, S3, S4 or S5 in T. S7-1 and S7-3 are worth settling with the owner because they are about being found and about publishing, not about speed.
