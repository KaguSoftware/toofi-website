## Seen in a browser

Headless Chrome with the GPU on, against the dev server, on a desktop profile (1440 × 900) and a phone profile (412 × 915, touch). These are checks of behaviour, not timings.

| Check | Result |
|---|---|
| Shader programs built in the first frame the visitor sees | **0** on both profiles. Before, all of them: 51 on desktop and 30 on the phone profile (S1) |
| Where they are built instead | Desktop: 42 by the background compile, 8 on first use in warm-up frames. Phone: 27 and 4 |
| Draws to the screen before the first real frame | 0, by design: the rig takes the first draw to the screen as "scene live", so warm-up frames never reach it |
| Story stills fetched on the live path | 0 (were 1 on the phone, 2 on desktop) |
| Preload hints in the head when the page has loaded | The tier's far model and the two decoder files: low on the phone profile, high on desktop |
| Home → Compounds → back | Render calls a second: about 1,970 on Home, **0** on Compounds, about 2,600 back on Home; no errors |
| Sound on, Home → Compounds → back | The audio context is running, then suspended (not closed), then running again; one context throughout; the button reads "Turn the sound off" on return |
| A link reported as 3g | Stills, "Load the 3D tour (about 6.1 MB)", no canvas, no preload; the button starts the live story |
| Save-Data | Stills, no offer, no canvas, no preload |
| The GPU context taken away (`WEBGL_lose_context`) | Stills and "Explore in 3D" within a second; the button starts a new scene, which runs |
| The name band | The traced word occupies the box the text did (x 207.98 against 207.97, width 536.38 against 536.39 px); English Home requests 2 font files where it requested 3 |
| Edit mode on `/compounds`, signed in as the demo editor | 6 editable fields and the toolbar; typing works; no errors |
| Arabic Home | The offer and the name band render mirrored, in Arabic |

One fault was found this way and fixed. Warm-up first drew the scene before the per-frame code had run, and three.js threw on a morph target that code prepares. The error was caught and reported and the scene still started, but the report was noise. Warm-up and compile frames now run one frame of the real loop at a standstill (`advance(0)`), so the scene is in the state its own code keeps it in.

## Tests

`npm run check` passes: typecheck, lint, the test gate, and 1,486 tests in 153 files (1,319 at the start of the track). New files each have their test beside them: `monitor.test.ts` (17), `compileAhead.test.ts` (15), `early.test.ts` (39, among them 26 devices on which the early script and `capability.ts` must decide alike), `lazy.test.tsx`, `client.test.ts`. `components/editable/client.ts` left the untested baseline.

Two tests outside the experience were changed, without weakening them: `SiteHeader.test.tsx` and `TweaksPanel.test.tsx` looked for edit-mode fields in the same tick as the render. The fields now load on demand, so the tests await them. The first also gained an assertion it lacked (that the editable field exists).

## Thresholds set without a device

Three numbers come from the search's estimates, not from hardware (D10, D18). Each is a named constant, so the first real measurement changes a number and not the code: `WEAK_GPU` and `PHONE_SHORT_SIDE` in `capability.ts`, `STARVED_FPS` in `monitor.ts`, and `LIVE_DOWNLOAD_MB` in `early.ts` (the sizes the offer names: 3.6 and 6.1 MB, from the rig after F2A; update them when RS has measured the fixed site).

One choice goes beyond the ledger's wording and is worth the owner's eye: T12 sends every device whose main pointer is a finger to the low tier, which includes tablets. The ledger says "the screen's short side or a coarse pointer"; a tablet has a short side over 768 px, so only the pointer rule catches it.
